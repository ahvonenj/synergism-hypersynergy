# Game dialogs: hidden dialogs and the mod code that answers dialogs

## The game's queue and the dialog hook

- **All game dialogs share one first-in, first-out queue.** `Confirm`, `Alert`, `InfoAlert`, `Prompt` and `PurchasePrompt` go through a single `AsyncQueue` (`UpdateHTML.ts`): a dialog only opens once the previous one is answered. `Notification` is not queued. Neither are the offline popup, the corruption cleanse confirm (`#corruptionCleanseConfirm`) or the game's other ad-hoc overlays.
- **Every queued dialog is shown inside `#confirmationBox`.** The queue only holds waiting dialogs while one is open, so a hidden `#confirmationBox` means the queue is empty.
- **On an idle queue, a dialog opens synchronously.** `enqueue` → `dequeue` → `action()` runs without an `await` before the dialog is shown. Checking `#confirmationBox` and then clicking in the same synchronous step cannot be raced, and the dialog is visible right after the click returns. This depends on the `AsyncQueue` implementation, so treat it as a speed-up, not as something correctness relies on.
- **Many game actions chain dialogs after an `await`.** For example, entering or leaving an Exalt asks a `Confirm`, then shows an `Alert` once it is answered (`SingularityChallenges.ts`). The second dialog is queued a microtask later. Player input can't slip in between, because the whole chain runs in microtasks of the same task. Code that is itself running in microtasks (an `await` chain in the mod) can. Exception: chains that pass through real asynchronous work, like file imports (`importData` awaits `file.text()`), so the tree import's result Alert comes in a later task.
- **Every successful ambrosia loadout load shows an `Alert`.** Loading in load mode goes through `createBlueberryTree()`, which ends with `Alert('ambrosia.importTree.success')`, the same text as a tree import. So every loadout switch (Auto-Loadout, autosing, imports, the heater's slot row) queues an Alert, and code reading that Alert's text (the bookmarklet path of Quick Import) can't tell its own import from a loadout switch.
- **Ambrosia loadouts can be written without SAVE mode or dialogs.** The game saves a loadout as `player.blueberryLoadouts[n] = tree` with no check; it only validates a tree when loading it (`validateBlueberryTree`, exposed by the patcher as `__HS_validateBlueberryTree`, which only reads the player's state). An empty tree `{}` is invalid, so an empty slot can't be loaded. `#blueberryQuickSave` saves the live tree into the active slot (`lastBlueberryLoadout`, marked by the `activeBlueberryLoadout` class; none right after a page load). So the mod never needs to toggle `#blueberryToggleMode` to SAVE, except the bookmarklet path of Quick Import for several lines.
- **The game's own confirmation toggles remove dialogs entirely:** `toggles[31]` (ascend and ascension challenges), `toggles[32]` (ant sacrifice), `toggles[33]` (singularity), `toggles[35]` (hepteract confirms and alerts), `shopConfirmationToggle` (shop and potions). Exalt, loadout and code dialogs have no toggle.
- **The patcher's dialog hook covers all 5 queued dialogs** (`__HS_DIALOG_HOOK_PATCHED`). It finds each one by its wrapper id (`confirmWrapper`, `alertWrapper`, …). When a dialog is queued, an extra default parameter calls `window.__HS_dialogOrigin(kind, firstArg)`. When it reaches the front of the queue, `window.__HS_onDialog(kind, origin)` returns `{ value }` to answer it without showing anything, or `undefined` to show it. An answered dialog still waits for the dialogs ahead of it, so a dialog left open (by the player, or a `PurchasePrompt`) blocks answered ones too. All 5 are patched or none.
- **`HSGameDialogs` (`hs-core/dialogs/hs-game-dialogs.ts`) is the mod side of the hook.** When a dialog is queued, it records its origin: the mod session claiming it, if any, and whether autosing is active (`setAutosingActive()`, set by autosing for its run, Restart included). It answers session dialogs, cancels or dismisses orphans (dialogs whose session ended before they reached the front), and keeps one lock for longer actions (`run`, waits for an idle queue, first come first served). `act(owner, answers, fn)` is for synchronous actions. While autosing is active, every other Confirm is answered OK and every other Alert dismissed, the player's included; InfoAlert, Prompt and PurchasePrompt are shown. Without the hook, sessions answer through the DOM (only dialogs that open within the act's task; one opened during `fn` itself is answered right after `fn`, still inside the act, because a nested synthetic click's observer callback only runs under the outer event), and autosing uses `HSGameDialogs`' dialog watcher (bookmarklet, or a patch older than the hook). Rejected options: "Decisions" below.
- **`window.event` stays set during the microtasks of a trusted event.** A dialog chained after a player's click (queued in a microtask) still sees that click as `window.event`. `HSGameDialogs` relies on it so that an `act` run from a player's click still claims the dialogs chained after it, and only those.
- **Autosing depends on that queue at every singularity.** `#enterAndLeaveExalt()` clicks Exalt 2 twice, and each click queues a `Confirm` followed by an `Alert`. `#waitForExaltState()` has no time limit, so a dialog blocking the queue freezes autosing at the end of a singularity until it is answered or autosing is stopped.

## Hidden dialogs

- **Hidden dialogs (`HSHiddenDialogs`, `hs-core/dialogs/hs-hidden-dialogs.ts`, setting "Hide game dialogs", off by default).** A checkbox above OK in the game's Confirm and Alert ("Always confirm" / "Don't show again") remembers the dialog's translation key when the player presses OK (click, Enter or Space) with it ticked; from then on it's answered OK / dismissed without being shown. Order in `HSGameDialogs`: a session's claim, then autosing, then shown while a `run()` holds the lock (decided when queued), then hidden, then shown. The key is found from the dialog's text by `HSDialogIdentity` (`hs-dialog-identity.ts`): a reverse lookup built from the game's translation file of the current language (English for missing or empty keys), exact texts in a `Map`, `{{placeholder}}` texts as anchored patterns, most specific first, too-short ones (< 10 fixed chars, CJK ×3) left out; it returns every key sharing the text. Both sides are normalised against the game's i18next post-processors (StatSymbols "☌ Blueberries", ColorText `<<color|text>>`, NumberLocale `num:((…))`, `$t()` nesting). Dialogs with no key get no checkbox. Turning the setting on adds the ready-made list (`resource/json/hs-hidden-dialogs.json`, each entry added once, tracked in `presetAdded`); the same file lists blocked dialogs (Time code Alert, cloud-save overwrites), never offered nor answered. The list is under its own `HSStorage` key (`hidden-dialogs`), not in the settings, and shown in the panel (UI page, "Hidden dialogs", click to forget, "Restore default" resets it to the ready-made list exactly). The notifications switch and the list are indented under the main switch and not shown while it's off (CSS only: `:has()` on the main switch's `.hs-disabled`); their stored state is untouched. "Show as notifications" (`hideGameDialogsNotify`) shows a hidden Alert's text with `HSUI.Notify`, in the bottom-left column: away from the mod's own messages, so a burst can't push them out. Without the hook, a hidden dialog is clicked once shown (the Confirm/Alert wrappers and texts are observed). Quick Import's fallback (no `exposedPlayer`) runs inside `run('quickImport')` so it can still read its Alert.

## Mod code that answers or fills dialogs

- **Mod code that answers or fills dialogs.** All of it goes through `HSGameDialogs`, except where noted:
  - `act` (synchronous click, its dialogs answered): ambrosia slot loads by Auto-Loadout and the heater results' slot row (`#reloadLoadoutSlot`, Alert dismissed; the loadout is loaded synchronously, so Auto-Loadout's switch from its capture listener is in place before the game's code listener runs, whoever clicked), hepteract quick expand (Cap then Craft Max, Confirm OK and Alerts dismissed; refused while a dialog is open; the player's `#toggle35` is no longer changed), potion "BUY 10x" (reads the shop's buy mode: Buy ANY = one click, Prompt `10`; Buy 10 = one click; Buy 1 = 10 clicks; Buy MAX refused; Confirms OK, "not enough quarks" Alerts shown), Add x10 (Prompt `10`, Alert dismissed), autosing's stop inside Exalt 2, autosing's Exalt exit at start (started inside an Exalt: a `window.confirm` asks the player first, then the active Exalt's icon is clicked, Confirm OK and Alert dismissed), Quick Import's slot reload.
  - A `prompt: { ok }` answer claims only the first Prompt of its `act`: e.g. Add x10's sum Prompt (calculator not maxed) is shown to the player.
  - Auto-Loadout (Add/Time capture listeners in `HSAmbrosia`) doesn't run while autosing is active (autosing sets its own loadout before using the codes). Time: its Confirm and Alerts are answered at once (an `act` around the loadout switch; the game's listener runs next for the same click event, so its dialogs are claimed), unless `exposedPlayer` shows Cx11 (`cubeUpgrades[61]`) below 100: then an instant answer always loses (the window is at least 6 s away), so the dialogs are shown, with a notification. Cx11 goes back to 0 at every singularity (ascensions keep it), so it's checked at each click. Add and Time load the previous loadout back once `HSGameDialogs.whenQueueIdle()` resolves (the code's dialogs are over), unless the player switched meanwhile or autosing started. The previous loadout is the slot shown as loaded (`#shownLoadoutSlot`), also when the game marks none: its saved loadout is loaded back even if the tree had changed since (restoring only with the game's mark would restore nothing after every singularity).
  - `HSGameDialogs.whenQueueIdle()`: resolves once the queue is idle, checked one task later (so dialogs answered at once have chained theirs). Takes no lock.
  - Autosing without any patch (bookmarklet): its Confirms and Alerts are clicked as they open, by the observer on the Confirm/Alert wrappers and texts (`#checkShownDialog`, before the browser paints, at most 20 in a row within one task), with a 250 ms poll as a safety net. Both only while autosing is active; they stop at once with it.
  - Autosing with a patch older than the dialog hook (Steam, not re-patched): the same watcher; autosing keeps its fast paths (each one only needs what it reads: stage function, live player, max challenges), the watcher closing each dialog before autosing's next step runs. The legacy auto-confirm (`__HS_AUTO_CONFIRM`, the hidden `autoConfirmPopups` setting) was removed from the mod and the patcher: a mod older than v2.14.4b-dev4 on the current patcher gets no auto-confirm.
  - Quick Import and the heater import (`HSAmbrosia`): with `exposedPlayer`, no dialog at all. They write `player.blueberryLoadouts[n]` directly, after the game's own check (`__HS_validateBlueberryTree`, patcher), then load the slot shown as loaded if it was written (`act`, Alert dismissed), so the game marks it (rainbow). Safe during autosing. Without `exposedPlayer` (bookmarklet): through the game's import, reading its result `Alert` and clicking the overwrite `Confirm` through the DOM, SAVE mode for several lines, refused during autosing. **The slot shown as loaded** (`#shownLoadoutSlot`, rainbow or silver border on the game's header module and the Ambrosia tab): the one the game marks, else the mod's own. The game marks none after a page load or any save load (singularities included): then it's the guess from the save at load (silver border, 80 % match or better), or the slot loaded before the save load. A single loadout goes into it on both paths (the success notification names the slot: a wrong guess is seen at once), and is refused only when no slot is shown; the bookmarklet path saves through SAVE mode there, as the game's quick save only targets its marked slot. Several lines go into slots 1 to 16, and the shown slot is loaded if written. Not refused without the game's mark: Import All then loaded nothing, and a player read the old tree on screen as "Import All doesn't import".
  - GQ distributor (`HSGQDistributor`, `hs-qol-buttons/hs-gq-distributor.ts`): runs inside `HSGameDialogs.run()`, shows each `PurchasePrompt` and fills it through the DOM, and its session dismisses the purchase Alerts. A `PurchasePrompt` left behind is cancelled as an orphan.
  - Not through `HSGameDialogs`: the Buy MAX button fills the `PurchasePrompt` the player opened; `HSCodes` rewrites the promo-code `Prompt` label.

## Decisions

The dialog queue's rules:
- While autosing is active, every Confirm is answered OK and every Alert dismissed, the player's included; InfoAlert, Prompt and PurchasePrompt are shown. Decided when the dialog is queued.
- Features answer only their own dialogs, through sessions (`act` for synchronous actions, `run` with one first-come-first-served lock, no priority); dialogs of an ended session are orphans (cancelled or dismissed).
- Loadouts are never toggled to SAVE mode where `exposedPlayer` exists: `player.blueberryLoadouts` is written directly.
- Hidden dialogs: OK only, Confirm and Alert only, no checkbox without a translation key, "Restore default" resets to the ready-made list exactly.
- **No auto-confirm** (the old `__HS_AUTO_CONFIRM` and hidden `autoConfirmPopups` setting were removed from the mod and the patcher). Autosing's fast paths don't need the hook: autosing never waits on dialogs, and without the hook the watcher clicks each one in the same task, before autosing's next step (traced on the Exalt entry: the Confirm clicked in `actFor`'s `finally`, the Alert by the observer at the next microtask checkpoint).

Tried or proposed, and dropped: autosing pausing on the player's dialogs (for good, also as a later add-on); checking the PL-AT calculator level 5 / Cx11 maxed at autosing start; tagging each dialog's origin as player / mod / game with a chained-dialog rule; the Exalt under the lock; turning the game's confirmation toggles off with a restore at load; toasts for game alerts; per-feature modes (concurrent / pause / refuse / at singularity end); lock priority; a pause API for features; a per-run `AbortController` or run object (also for autosing, `docs/features/autosing.md`).

Left as is: a claimed dialog queued behind a player's dialog can't be fixed without the hook. A claimed dialog opening as another closes was withdrawn as theoretical.
