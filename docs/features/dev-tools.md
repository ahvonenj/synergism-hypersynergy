# Dev tools (dev builds only)

`HSDevTools` (`hs-core/dev/hs-dev-tools.ts`) adds rows to the Debug tab that edit the live player object (`exposedPlayer`), to set up a save for a test. It must never reach players. The Debug tab itself exists only in dev builds: the release build removes it (`HSUI.removeTab`).
- **`HS_DEV_BUILD` keeps it out of the release.** esbuild defines it as `false` for `release` and `true` for `build` and `dev`. The only use of `HSDevTools` is under `if (HS_DEV_BUILD)` in `#buildDebugTab`, so the release build drops the class. It is a build-time constant, so a player can't turn it on. (The old runtime flag `window.__HS_IS_DEV` / `HSGlobal.General.isDev` was unused and is removed.)
- **The release build checks it.** `esbuild.config.js` builds the release in memory and refuses to write the bundle if it contains `hs-dev-tools`. Keep that string out of any code the release includes.
- **To stay droppable, the class has no static fields and no import that runs code when loaded.** It is not an `HSModule`: `HS_MODULE_DEFINITIONS` references every registered module statically, which would pull it into the release.
- **`HSAutosingRecorder`** (`hs-autosing/hs-autosingRecorder.ts`) follows the same rules: it keeps autosing's timings in
  `window.__HS_autosingTimings` for the headless harness (`autosing-run.cjs` writes them to `timings.json`), every
  call under `if (HS_DEV_BUILD)`.
- **A row is a path into the player object** (`worlds`, `hepteracts.quark.BAL`, `cubeUpgrades.61`). Writing depends on the value's type: plain number, the game's `Decimal` (built with the value's own constructor), `QuarkHandler` (`reset()` then `add(n, false, false)`), `Cube` (`sub()` then `add()`, capped at 1e300 by the game), boolean, string. A path that doesn't lead to an existing single value is refused.
- **The suggested value** (greyed in an empty field, used by Set) is 1 followed by the current exponent + 5 (6e7 gives 1e12). Levels, counts and pinned rows get none. A typed value is not remembered: after a Set, the field is emptied and shows the next suggestion (rows without a suggestion keep the text until a reload). `HSStorage` key `dev-tools` only holds the pinned paths and the path row's last path.
- **The first edit of a session takes a snapshot of the save** (`HSBackup.captureSave`), kept in IndexedDB (`hs-dev-tools`). "Download latest snapshot" gives a file for the game's Load from file.
- **Snapshots are automatic or named.** Automatic: before the first edit, and before each restore; the last 5 are kept, both sorts together. Named ("Save snapshot"): the current state under a name, never removed on its own; saving under the same name replaces it. The list shows every stored one, latest first, with Restore, Download and Delete. "Import file" adds a save from the disk (a game export, or a mod backup's save, read by `HSBackup.saveFromFile`, so the same files as the backup import) as a named snapshot under its file name, dated from its `offlinetick`; it is only loaded by its Restore.
- **Restore goes through `HSBackup.importSaveAndReload`**: the snapshot is written as the game's stored save, then the page reloads (see "Backup"). Before that, the current state is stored as an automatic snapshot. Refused while autosing is active.
- **"Skip offline progress" (a checkbox by "Import file", ticked by default, remembered with the pinned fields) sets how Restore loads.** Unticked: the save is written unchanged, so it loads as the game loads any save at a page load (offline progress, code timers counting the time away, daily reset on a new day). Ticked: every clock field of the save moves to now (`HSBackup.shiftSaveClock` with the code timers and the daily reset, see "Backup"), so the state loads as it was saved, with no offline progress, the same code timers and no daily reset. The player's import skips only the offline progress.
- **The two singularity rows are live edits, no reload** (`singularityCount`, `highestSingularityCount`). The game's Elevator does the same plain write going down, and autosing at each singularity. The two counts are kept in line whatever sets them (row, path row, `hsDev.set`): a count above the highest raises the highest, a highest below the count lowers the count. Whole numbers only. Allowed inside an Exalt too (an easier Exalt for a test): there the game sets the count from the Exalt's requirement when it is entered and at every load, so an edit lasts until the next reload. What the game derives from the count is read when needed; what the highest unlocks is shown or hidden by `revealStuff()`, which runs at every tab change. Not redone by an edit: the Elevator panel's text (until it is opened again), singularity achievements (checked at load and at a singularity), the free upgrade levels given once at singularities 5 and 10.
- **The Snapshots title has a "?"** listing these rules on hover (`SNAPSHOT_RULES`): update it when a snapshot rule changes. It is the only help tooltip: only rules that can't be seen on screen get one.
- **Console:** `hsDev.set('cubeUpgrades.61', 0)`, `hsDev.get(path)`, `hsDev.snapshot('name')`, `hsDev.restore('name')` (named snapshots only).
- The game doesn't recompute what derives from an edited value, and hidden tabs stay stale.
- Deleting a named snapshot asks a confirm, an automatic one doesn't. Steam achievements unlocked by an edit are not a concern.
- Tested headless: the real class in Chrome against a fake game (stubbed `HSModuleRegistry.getModule`, `HSUI.Notify`, `HSLogger`, `HSBackup.importSaveAndReload`), driven over the DevTools protocol (`--dump-dom` doesn't wait for IndexedDB).
