# Ambrosia Heater

The heater docs: `heater.md` (the panel: heating, results, branches, inputs, Best H), `heater-optimizer.md` (how the optimizer models the game, row scores, speed, known limits).

`hs-modules/hs-heater/`: Ambrosia loadout optimizer. It runs in a web worker built separately (`hs-heater-optimizer-worker.ts`), driven by `HSHeaterOptimizerRunner`.

## Heating
- **A heat is logged in the Log tab**: one summary line with a time per worker group, or "result reused" for an input already heated.
  - With debug on, one more line per group with the optimizer's stage times (`Heat stages, cubes+sr: …`, stages under 0.05 s left out; a parent stage comes after its sub-stages): the worker calls `runExperiment` and sends `diagnostics.stages` back (no stage on the heat button: it is full).
  - The optimizer can't import `HSLogger` (no DOM in a worker): its stand-in keeps `warn` and `error` lines (`takeHeaterOptimizerLogs()`), the worker sends them back with its answer, the runner writes them.
  - A failed heat logs its input as JSON (runner) and the stack (the heat button's catch). The optimizer's crash dump stays console only.
- **A heat can be cancelled** (✖ right of "Heating…", shown only while the optimizer runs in a worker): `HSHeaterOptimizerRunner.cancel()` terminates the running worker, `createResult` rejects with `HSHeatCancelledError`, nothing is cached and the groups already heated are dropped. One "Heat cancelled" log line, no notification.
- **The heat button shows the elapsed time** in whole seconds, and the number of worker groups started when there are several (`🔥 Heating 2/3... ⏳ 12s 🌡️`, from `createResult`'s `onProgress`, called before each group). It only ticks with a worker; without one the page is frozen and the label stays as it is.

## Two workers
- "Faster heat (2 workers)" checkbox right under the heat button (hidden setting `heaterTwoWorkers`, on by default; hidden without a worker), its warning in the title.
- `BRANCH_GROUPS` gives each group a lane: lane 0 Hyperflux then Cubes+SR (the two big ones, ~0.8 GB each, never at once), lane 1 Oct+AmbOct (Max Amb + Oct is in the Oct group: it shares Oct's tables), Luck+Purple, Quarks/Obt/Off. Each lane runs its groups one at a time.
- Measured: S260 in node 96 → ~57 s, peak ~1.3 GB summed instead of 0.9; Chrome's Task Manager showed at most 1.1 GB on a save at 144M Ambrosia.
- Falls back to one worker when `navigator.deviceMemory` < 8 or `hardwareConcurrency` < 4 (unknown = enough), said in the summary line.
- A failing group stops the other lane; a cancel stops both. Results are merged by group index, so the order doesn't depend on which lane ends first.

## Results table
- **Effect** is text, formatted in the worker by `formatNumber` (`hs-heater-utils.ts`) with the browser's number format; the results renderer prints it as is.
- **Headers**: Cost is the Ambrosia icon (16 px), Types is "Loadout", Loadout is "Actions". The p4x4 section's Effect header carries a cube icon (`TinyWow3.png`, `buildArraySectionHeaderRow`): its rows (H, SR1, SR2) all show cubes. No icon on each Effect cell: redundant with the type label in Common, wrong in Exalt 10 where Blue/Red mean time, and too wide for the Purple split cell (fixed 3.4em). The Hybrid "Oct Effect" header stays text.
- **Purple rows**: the four Purple types are the last rows of "Common Loadouts" (no Purple section). When one of them is in the results, that section's Effect and Routing are one cell spanning both effect columns, split by CSS (`.hs-heater-split-cell`), so the routing's width doesn't set the p4x4 section's columns; the other rows leave the routing empty. With no Purple row, the section has no Routing column.
- **Max SR1 / Max SR2 rows**: the Effect is the tree's cube multiplier, like the H rows (Hyperflux at P4x4 50, Tau), so players can see what maxing SR costs in cubes (`generateOutput`'s `effectStat`). "Maxed?" stays "SR at its max level". The Types cell shows the SR level ("Max SR1 (1/2)", `labelLevel` in the type config, read from the row's tree by the renderer; the select labels and semantic ids don't change). The Effect's title gives the penalty SR lifts (Obtainium/Offerings and Cubes factors, `withPenaltyReliefTitle`, row element 8). SR1 is heated as outside an Exalt and SR2 as inside one, whatever the heat's Exalt: their descriptions say so. No SR level within budget: Unaffordable. The H rows already take SR when it raises cubes, so Max SR1 is often the very H7 tree.
- **An H row showing "Never" is dimmed** (`.hs-heater-never-row`, opacity on its cells), also when a slot picks it, so the rows that can win stand out: often only 2-4 of the 8 can. No setting: the table is the mod's own. Not a grey text colour: the ✔/✘, icons and buttons wouldn't follow it.
- **"Maxed?" compares with a tree that can exist**: an H row's maxed tree drops upgrades whose prerequisites its Hyperflux level doesn't meet (`dropUnmetPrerequisites`; SR1 needs Hyperflux 4 and raises Cube pre-AoAG, so H0-H3 would otherwise always be ✘).
- **"Phoney (best econ)" / "Pamb (best econ)" are ✓ whenever `barIncomeHighBudget` applies**, as the Purple rows are: the ✓ comes from the budget (more Ambrosia can't help), not from which search found the tree (comparing against `fullAllAmbLoadout()`, which the player can't afford, always gave ✘). Rejected: rerunning the exact enumeration (`findAffordableFullLevelBarIncomeOpts`) at the best routing, +0.4 s per Purple heat (2.65 → 3.05 s on a S285 save) for the same tree there; worth it only if a player reports a worse best econ tree.

## Unaffordable and ✘ rows
- **A type the player can't afford** is still in the results, as an "Unaffordable" row with no loadout.
- **"Your loadout order" borders**: red + unticked checkbox = the type is missing from the results (its branch wasn't heated); orange + unticked = Unaffordable. A type picked there and Unaffordable has its whole row in the orange of that slot's border (`#c96a00`).
- **Import All** skips an unticked slot silently and leaves it as it is; an Unaffordable type the player ticked again is skipped with a warning (notification and log).
- **An Unaffordable row names the short resource** (chosen over a tooltip): its Blueberries and/or Cost cell shows what the tree needs, in the ✘ red, with "You have N" as title; a resource that isn't short stays "N / A". The worker sets it (`unaffordableRow(needed, atLeast)`, the row's optional 8th element `shortfall`). Exact for Max Amb + Oct (the full All Ambrosia base, a valid row on its own) and `generateOutput`'s checks; a minimum, shown "≥", for H rows (Hyperflux at that level alone) and SR1 (SR1 + its Hyperflux 4). Neither short (no tree fits for another reason): both "N / A".
- **A ✘ row says what limits it** (icon version chosen; the richer "next step" title was declined): the game's Ambrosia and/or Blueberry icon after the ✘, titles "More Ambrosia would raise it" / "More Blueberries would raise it"; both = either would.
  - `Loadout.limitingResources` tries +1 level of each upgrade (prerequisites included, never above `maxLoadout`'s levels) on a copy: a stat-raising try that needs more Blueberries than are left → Blueberries; one whose Blueberries fit but not its Ambrosia → Ambrosia. No measurable time (node bench, S260 save).
  - The renderer shows them only on ✘: the bar-income rows whose ✔ is set afterwards can carry them.
  - An Unaffordable row's ✘ takes the same icons from its `shortfall` (renderer only), titled "Not enough Ambrosia" / "Not enough Blueberries" (there, both = both needed); no shortfall → bare ✘.

## Branches
- **The "Purple Ambrosia" checkbox** (inputs modal) is only there when the save has an Exalt 9 completion (`exalt9Unlocked` in the heater data, the game's own unlock condition); otherwise the branch is off.
- **The title is "Loadouts to heat:"**, for ordinary players; "branch" stays the word in code and docs (not "Heat for": the left column's heading).
- **Three grey glyphs at the right end of the "Loadouts to heat:" line** (two glyphs rather than one toggle, the slots one added first): ☰ ticks exactly the branches of the slots that have a type and unticks the rest, ☑ ticks all, ☐ unticks all. They act on the checkboxes shown only (a locked Purple is left alone), and save like a click.
- **The checkboxes are remembered**: the hidden setting `heaterUncheckedBranches` holds the branches the player unticked; a branch never unticked starts ticked (first open, a new branch, Purple once unlocked).
  - Setting a slot's type ticks that type's branch (Best H = Hyperflux), and that is saved too. Only that slot's branch, and nothing at open: slots change only in the modal, so ticking the other slots' branches could only undo the player's untick (tried: Quarks and Oct got re-ticked at open).
  - Nothing is ever unticked for the player; unticking a branch a slot needs is allowed (the slot's red border after the heat says it). A red background + 🔥 on a branch a slot needed was tried and removed.
- **Slow branches start unticked** (`startsUnticked` in `HEATER_BRANCH_DEFINITIONS`, today only Obt + Off): the hidden setting `heaterTickedBranches` holds the player's ticks of such branches, `heaterUncheckedBranches` the unticks of the others. "(slower)" in grey after the label (`labelNote`).

## Exalts
- **The Exalt badge** (left of the results topbar, opposite `?`) shows when the heat's `input.exalt` has an entry in `HEATER_EXALT_RULES` (`hs-heater-result-config.ts`), today only Exalt 10; its tooltip says how the results read in that Exalt. Chosen over piling Exalt rules into the type descriptions. Other Exalts get an entry only after checking what the optimizer does in them against the game.
- **Exalts are shown by name, never by number** (`HEATER_EXALT_OPTIONS` / `getHeaterExaltName` in `hs-heater-input-config.ts`; the select, the two "x1 Done" inputs, the warning, the Exalt badge): the game's numbers disagree with each other (code order, unlock order, and its own text calls No Ambrosia Upgrades "EXALT 5"). The values stay GDS's `getActiveExalt()` numbers (by unlock singularity), which the optimizer's rules use.
- **The Exalt select drives every Exalt rule of the optimizer**, No Quark Upgrades included: `shopUpgradesDisabled` is `exalt === 4` in the worker, not the export's flag (GDS still exports it, unread). The base fields (luck, bar speed, quark, cubes…) still come from the exported save as it was, so a line under the select ("⚠️ Base values come from a save in <Exalt name>" / "outside any Exalt") shows while the picked Exalt differs from the export's `exalt` (`HSHeaterUIInput.refreshExaltWarning`; in the modal, not a notification). Removing the shop part from the bases (export shop-free values) was left out.

## Inputs modal vs hidden inputs
- **Height**: it opens as tall as its right column needs, at most down to the screen's bottom (`#fitHeightToRightColumn`, measured, not a fixed height: the column depends on the loadout count); the left column scrolls. Anything added to the right column counts by itself.
- **Width**: no fixed width, both columns follow their content. Left: the longest label and the Exalt select (inputs at least 140px). Right: its widest line, today "Faster heat (2 workers)"; the slot dropdowns take what the row leaves. The slot label is 18px, 24px from 10 slots on (L10 doesn't fit in 18).
- **Field order**: players rarely read the inputs, so the few they may change on purpose come first under "Heat for" (Exalt?, Current Singularity, Active Bells, Event Blue Bar Bonus, Post-AoAG); no more fields there. Then Blue Ambrosia, Red Ambrosia (bar fields with their luck/speed), Red Ambrosia Upgrades, Resources & Singularity, Runes & Talismans, Unlocks (moved down from second), Shop last. A grey heading row comes from `heading` on a group's first field in `inputDefinitions`; nothing reads the list by position.
- **Every modal field reaches the optimizer.** The optimizer reads hidden export data (`shopUpgradeRawLevels`, `shopBonusLevelsNoAmbrosia`, `panthemaLevel`): `fillStatsAndOptionsFromInput` overlays the modal's shop levels onto `shopUpgradeRawLevels` and its Free Quark/Infinity levels onto the Quark/Infinity groups (GDS exports equal values on both sides, checked on 8 backups). "Jack of All Trades Level" (`panthemaLevel`) replaced the Jack checkbox; GDS still exports `jack` (unread).
- **The inputs left out of the modal on purpose**, with their reasons, are listed in the `HeaterInputBase` comment (`hs-heater-input-config.ts`).

## Best H (current P4x4)
- **A slot choice, not a result row**: "Best H (P4x4 now)" (`hyperflux:best`, `HEATER_BEST_H_SEMANTIC_ID`) sits after H7 in the "Your loadout order" dropdowns. `HSHeaterResultStore.resolveSemanticId` turns it into the H row that wins at the live P4x4; every reader of a slot's choice goes through it (availability borders, unaffordable check, Import All, results highlight). Sync Icons and Sync Settings keep the raw id (Hyperflux icon; Autosing Early Cube preference after H7, before Oct).
- **The rule** (`pickBestHyperfluxRowIndex`): the highest H row whose "p4x4 eq" is a number ≤ P4x4. The optimizer's thresholds keep only rows that win somewhere, with strictly rising p4x4 eq; the others show "Never", unaffordable ones "N / A". No row qualifies (all unaffordable): H0, shown as unaffordable. No H rows, or P4x4 unknown: unresolved, red border, and Import All skips it with a warning.
- **P4x4 is read live**, at Import All (once for every slot) and at each draw of the results table: `exposedPlayer.platonicUpgrades[19]`, else the last GDS save. Not the heat-time value: P4x4 (max 50) resets at every singularity and climbs during it, and long sings (new highest, Exalts) make a mid-sing pick useful. The pick is made once: nothing re-picks when P4x4 crosses a threshold later (not wanted for now).
- **"★ now"** in the p4x4 eq cell marks that row in the results; its title gives the P4x4 used. The table is redrawn at each heat and slot change, not when P4x4 moves. Import All notifies and logs "Best H at P4x4 N: L3: H5".
- **To test it**, change P4x4 through the Debug tab's live edits, then change a slot dropdown to redraw the results.
